(2) 🔴 **A licence gate must bind its verdict to the payload's opening declaration, not to any licence name appearing anywhere in the file** — otherwise the EUPL, which is precisely the family this shelf has just started carrying, is the family it will silently mis-grade. Same class as `659-P` (naive pipe-count: `66` reported, `1` real) and `660-T` (`13` header-shaped rows, `0` real): **calibrate against the payload shapes this base actually holds before trusting a verdict.**

🔵 **And it refines `665-H`.** p665 recorded that `gh api` reports `NOASSERTION` for all seven repositories it read and concluded the API *hides a whole licence family*. p666's enumeration shows the API reports `EUPL-1.2` **correctly** for `compleap` — the one repository in `100` it gives an SPDX for at all. 🟢 **So `NOASSERTION` here tracks the payload's *form* — a short "Licensed under the EUPL, Version 1.x" reference — not the EUPL family itself.** The API can recognise the EUPL; it cannot recognise a pointer to it.

🔴 **What the EUPL does that MIT and Apache-2.0 do not.** It is a **copyleft** licence, so a derivative is licensed onward under it. The clause that matters commercially is its own definition of distribution: the EUPL treats **“Distribution or Communication”** as including making the Work available to others **by any means, online included** — so standing a modified EUPL service up as SaaS is the trigger, in the way AGPL-3.0 works and GPL-3.0 does not. ⚠️ **Provenance of that reading, stated because this page's own rules require it:** the grant *references* on the four rows were read first-hand at p665; **the EUPL text itself was not.** `joinup.ec.europa.eu` — the host all four payloads point at — **fails `getaddrinfo` under this session's network policy**, the same class of block p664 recorded against `zenodo.org` and `cambridge.org`. The characterisation above is therefore **secondary**, and `intel/open-gaps.md` **Gap 249** carries the first-hand read as an open action. 🔵 **Read Article 5 and the Appendix before architecting anything on these four rows**, and note the two upsides the appendix brings: a **compatibility list** (GPL-2.0, AGPL-3.0, EPL, MPL-2.0, LGPL, OSL, CeCILL, LiLiQ) that lets a derivative be relicensed onto a listed licence, and **legal validity in 23 EU languages** — which is why a European public buyer's procurement office recognises it and often prefers it.

🟢 **What this tier is worth anyway, and the shape that keeps the obligation off your code.** Do not fork these services. **Integrate against them**: they are a national ministry's *production* learner stack — applications (`ataru`), statutory personal competence plans (`ehoks`), the machine-readable national curriculum (`eperusteet`), attainments (`suorituspalvelu`), learner identity (`oppijanumerorekisteri`). An MIT/Apache agent layer that calls these over their APIs, in its own process, is not a derivative work of them. That pattern is written up as 🆕 **P32** in [`../compose/patterns.md`](../compose/patterns.md).

🔵 **And the channel lesson, third instance and the strongest yet: `gh api` reports every one of the seven as `NOASSERTION`.** p663 measured `NOASSERTION` landing on MIT, p664 on AGPL-3.0; p665 lands it on a whole seven-repository national-agency family carrying real EUPL grants. `NOASSERTION` means *GitHub's classifier did not match the text* — here, because the text is a four-line EUPL reference rather than a stock licence body. **It is not a licence verdict in either direction, and a tier was missing from this page for want of reading four lines.**

### Pattern F — Permissive institutional LMS, agents in-tree (greenfield HE, EMEA public sector) 🟢 new at p653
```
OpenOlat (Apache-2.0)          ← the platform itself is permissive: closed derivative allowed
```

**What makes this pattern different from every other one on this page:** it is the only one where **the institutional LMS itself is permissive and the AI plumbing is already in the tree**. Patterns A, B and C all exist to hold proprietary work *outside* a platform that cannot absorb it. Here there is nothing to hold outside — an agent can live in-tree, in the same build, and the deliverable can still be closed.

🟢 **The LLM subsystem is not a roadmap item; it is declared in `pom.xml`.** `langchain4j` 1.23.0 with the OpenAI, Anthropic and embeddings modules, verified by reading the manifest at first hand on 2026-11-04. The practical consequence for a data-residency engagement: **`langchain4j-open-ai` speaks the OpenAI-compatible wire protocol, which Ollama and vLLM both serve** — so an in-jurisdiction, no-egress deployment needs a configuration change and an endpoint, not a code fork and not a new dependency. There is no `langchain4j-ollama` module in the tree and it is not needed for that path.

🔴 **The one dependency that decides whether a closed derivative is actually clean.** Of 270 declared dependencies, exactly one is copyleft: **MySQL Connector/J** (`com.mysql:mysql-connector-j` 26.10.0), which is **GPL-2.0 with the Universal FOSS Exception**. The fix is already in the tree and costs nothing: **PostgreSQL JDBC 42.7.14 (BSD-2-Clause) is a first-class supported backend.** Specify PostgreSQL in the proposal and the tree is permissive end to end.

Verified absent, because in a Java LMS these are the usual killers and their absence is what makes the above true: **no iText** (AGPL-3.0), **no JasperReports** (LGPL). Hibernate is at **7.4.14** and hibernate-validator at **9.1.6** — both Apache-2.0 eras, not the old LGPL-2.1 Hibernate.

### Pattern I — Launch over LTI, record over xAPI, never fork the platform (best fit: any client with an incumbent LMS) 🟢 new at p656

The pattern that makes the other eight safe to sell. Every pattern above eventually asks the same two questions — *how does our thing appear inside the LMS the client already runs,* and *how do we prove it worked* — and until p656 this shelf answered neither.

1. **Get in over LTI 1.3, not through a fork.** `tsugiproject/tsugi` (Apache-2.0) for PHP, `dmitry-viskov/pylti1.3` (MIT) for Python, `jupyterhub/ltiauthenticator` (BSD-3-Clause) when the destination is a notebook. One integration launches inside Moodle, Canvas, Brightspace, Open edX, Sakai and OpenOlat. 🔵 **The licence consequence is the whole point: an LTI tool is a separate work that the LMS merely launches, so a GPL-3.0 Moodle or an AGPL-3.0 Open edX imposes nothing on it.** This is the same boundary P3 draws around XBlocks, generalised to every platform at once.
2. **Keep the client's content where it is.** `jcputney/scorm-again` (MIT) plays their existing SCORM 1.2 / 2004 / AICC / cmi5 packages. If they author in H5P or Adapt, both are **GPL-3.0 — integrate, never fork**; call their APIs and ship nothing derived from them.
3. **Record every interaction to a permissive LRS.** `yetanalytics/lrsql` (Apache-2.0) behind `RusticiSoftware/TinCanJS` (Apache-2.0) on the content side, against the statement shapes in `adlnet/xAPI-Spec` (Apache-2.0). Actor, verb, object, result, timestamp — per learner, per attempt. 🟢 **This is the deliverable that turns a pilot into a renewal**, and it is what `compose/patterns.md` P5 has been selling as "governance and measurement" without naming a component.
4. **Assess with the permissive option where the subject allows it.** `numbas/Numbas` (Apache-2.0) for mathematical and quantitative work; `oat-sa/tao-core` (GPL-2.0) only where QTI compliance is contractually required, and then client-operated.
5. **Accessibility is a client-operated deployment, not a product.** `ucfopen/UDOIT` (GPL-3.0) is the only real tool. Deploy it in the client's estate, bill the remediation work, ship no derivative.

**Licence position end to end:** steps 1–4 are Apache-2.0 / MIT / BSD-3 and can carry proprietary work. Steps 2 (authoring) and 5 (accessibility) are copyleft and stay stock. **Timeline 4–6 weeks** on top of an existing engagement; it is plumbing, and the components are small.

🔴 **Scope the single point of failure explicitly.** `lrsql` is the only live permissive LRS in existence — `learninglocker` is GPL-3.0 and dormant since 2024-05-30, `adlnet/ADL_LRS` is ~12 months quiet. Name that dependency in the proposal.

## 🔴 p659 — the public 2026 LMS guides print the wrong licence for Sakai, and this page is right

The mandated vertical-platform leg returned the current crop of “best open-source LMS 2026” guides. Two of them state that **Sakai is Apache-2.0**, and one presents it as *the* permissively-licensed institutional option on that basis.

🟢 **This page already carries the correct cell, measured at first hand:** `sakaiproject/sakai` is **ECL-2.0** — the Educational Community License v2.0 — read from the payload at `11,120 B`. No cell was changed at p659; the external claim was checked against this base and the base held.

🔵 **The distinction is not pedantic, and it cuts in the direction clients care about.** ECL-2.0 is an Apache-2.0 *derivative*: the permissions are substantially Apache's, but the **patent grant is narrowed** — where Apache-2.0 grants patent rights for the work generally, ECL-2.0 scopes the contributor's patent grant to the contributions as used in the licensed work, with the educational-context framing the licence was written for. For a Globant engagement that means: Apache-2.0 and ECL-2.0 are **both** safe for a closed derivative, so the build decision does not change — but **a client's counsel diffing your licence schedule against the project's actual payload will find a discrepancy if you copied `Apache-2.0` out of a guide.** Write `ECL-2.0` and cite the payload.

🔴 **The general rule this instance evidences.** A secondary source's licence claim is worth exactly nothing against a payload read. Of the licence claims this pass's vertical leg served, the one that was checkable against this base's own first-hand reads was **wrong**, and it was wrong in the *permissive* direction — the direction that gets a deliverable shipped before anyone notices. That is the same failure mode as **T38**, arriving through a different channel: not GitHub's classifier this time, but published human guidance.
